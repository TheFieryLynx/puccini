# TOSCA 1.3 concrete target capability matching

Sections 3.7.3 and 3.8.2 require a fulfilling capability on a concrete target.
Section 3.8.2.2.1 explicitly makes the short form conditional on its existence.
The extended form adds selectors; it does not remove the definition's contract.
Capability and node types use their effective derived_from hierarchy (3.7.7,
3.7.9). Relationship valid_target_types names capability types (3.7.10).

The specification does not give a tie-break for several compatible capabilities
on one concrete node. Rejecting every such template would impose an unstated
uniqueness requirement; selecting the first would impose an arbitrary binding.
Puccini therefore validates existence, binds a unique candidate in normalized
CapabilityName, and leaves CapabilityName unset when several remain. It retains
the node, capability type and relationship restrictions for subsequent binding.
The sorted admissible names are also serialized as capabilityNames. A type name
alone cannot retain the intersection of all restrictions: the normalized type
hierarchy does not carry relationship valid_target_types. The Clout resolver
therefore honors this optional admissible set. Other grammars omit the field.
This normalization policy is an implementation decision, not a quoted MUST.
Explicit symbolic names are checked directly and never replaced by a fallback.
A symbolic name coinciding with a type name is interpreted locally first, in
line with the collision policy for filters in 3.6.5.4; applying that precedence
to assignment selectors is an interpretation, not that clause's direct scope.

Section 3.8.2.2.3 explicitly forbids assignment node_filter with a concrete Node
Template. Such combinations are rejected regardless of filter values. Runtime
filter selection for abstract targets remains with the orchestrator; the
processor preserves filters together with capability and relationship limits.
The requested concrete filter success cases are consequently invalid grammar
combinations. No new runtime property-filter evaluator is introduced.

Omitted required assignments remain abstract obligations, as allowed by 3.7.3
and 3.8.2's runtime fulfillment model; they are not equivalent to an explicitly
bound incompatible node. Existing occurrence checks and complete intervals are
preserved. These decisions do not certify catalog completeness or the historical
223/223 claim.
