# 0010: TOSCA 1.3 attribute-default provenance

## Status

Accepted.

## Context

TOSCA Simple Profile in YAML 1.3 §3.6.12.4 requires values of an
attribute-definition `default` to be derived or calculated from another
attribute or operation output (actual state), and prohibits hard-coded values
and values derived from property settings or inputs (desired state).

The section does not define an algorithm for composite functions or structured
values. It also conflicts with the same pinned specification's normative Root
node and Root relationship definitions, which explicitly declare the
hard-coded attribute value `state.default: initial` in §§5.9.1 and 5.7.1.

## Decision

For user-authored TOSCA 1.3 definitions:

- `get_attribute` and `get_operation_output` are actual-state sources.
- `get_input` and `get_property` are prohibited desired-state sources.
- a calculating/composing function is valid when at least one nested
  actual-state source contributes to it and no nested desired-state source
  contributes to it;
- literal arguments used by such a calculation are allowed, because they are
  operands rather than the source of the complete default;
- a standalone literal is hard-coded and invalid;
- every leaf of a structured list or map default must independently satisfy
  the provenance rule;
- an inherited default is validated once at its declaring definition, while an
  explicit refinement default is validated at the refinement.

The pinned bundled TOSCA 1.3 normative profile is exempt from this general
validation only for declarations loaded through its internal profile URL. This
preserves the specification-mandated `initial` Root state defaults without
allowing user metadata or a copied declaration to bypass strict validation.

TOSCA 2.0 does not enable this policy.

## Parser phase

Validation runs during attribute-definition rendering, after function syntax
has been parsed and after inheritance has established the effective
definition. The validator checks only an explicitly declared local `default`,
so inherited declarations do not produce duplicate diagnostics.

## Consequences

Diagnostics distinguish hard-coded values from forbidden desired-state
functions and point to the offending nested value. Composite traversal and
diagnostic order are deterministic. This interpretation is an implementation
decision for language the specification leaves incomplete; it is not presented
as a direct quotation of the standard.
