# 0011 — TOSCA 1.3 substitution mapping coverage uses effective definitions

## Status

Accepted.

## Context

TOSCA Simple Profile in YAML 1.3 §3.8.13.4 says that a substitution mapping
MUST provide a mapping for every property, capability, and requirement defined
in the specified node type. The sentence does not explicitly say whether
“defined” means only declarations lexically present on that type or the
effective definitions after `derived_from` inheritance. It also does not say
whether optional properties or requirements with a zero lower occurrence bound
can be omitted.

The surrounding §3.8.13 grammar identifies the `node_type` as the type for
which the topology provides an implementation. The property, capability, and
requirement mapping sections resolve their names against that node type. Type
inheritance is processed before mappings are rendered, and all other semantic
uses of a node type operate on the effective inherited definition maps.

## Decision

For strict TOSCA 1.3 processing:

1. Coverage is checked against the effective property, capability, and
   requirement definitions after inheritance.
2. Every definition needs at least one corresponding mapping.
3. Property `required: false` and requirement `occurrences: [0, ...]` do not
   waive the mapping, because §3.8.13.4 says every definition without an
   optionality exception.
4. One mapping satisfies completeness for a requirement definition. Mapping
   multiplicity and occurrence-range rules remain separate validations.
5. Attributes and interfaces remain optional because §3.8.13.4 does not name
   them.
6. Missing mappings use the processor's deterministic canonical path order:
   sorted capabilities, sorted properties, then sorted requirements.

Items 1, 3, 4, and 6 are implementation interpretations selected to make the
MUST internally consistent with effective-type semantics; they are not direct
quotations from the specification.

## Implementation

Completeness runs during rendering, after type inheritance and after supplied
mappings have been structurally read and resolved. Shared rendering exposes an
optional policy hook, installed only by the TOSCA 1.3 grammar.

## Consequences

- A derived substituted node type cannot omit mappings inherited from a parent.
- Optional definitions still need mappings.
- Existing diagnostics for malformed, unknown, or incompatible supplied
  mappings remain distinct from missing-mapping diagnostics.
- TOSCA 2.0 behavior is unchanged by this TOSCA 1.3 policy.
