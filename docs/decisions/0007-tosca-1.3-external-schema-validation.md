# 0007: TOSCA 1.3 external property schema validation

- Status: accepted
- Date: 2026-07-28
- Applicable language version: TOSCA Simple Profile in YAML 1.3 only

## Context

Section 3.6.10.5 requires a string supplied by a property definition's
`schema` keyname to be a valid schema definition matching the recognized
external data type named by `type`. The next sentence permits, but does not
require, an orchestrator to validate property values with that schema.

The specification uses "external" for a data representation and schema
language outside TOSCA. It does not define the schema string as an external
resource identifier. Section 3.6.3.4 defines `schema_definition` as a schema
definition represented as a string. Sections 5.3.2 and 5.3.4 recognize the
external `json` and `xml` data types and show inline JSON Schema and XML Schema
documents.

This record separates the mandatory validation of the schema document from
the optional use of that document to validate a property's runtime value.

## Normative findings

1. Section 3.6.3, **Constraint clause**, defines `schema` as a constraint whose
   operand is a string and whose grammar operand is `schema_definition`.
2. Section 3.6.3.2, **External schema**, identifies JSON and XML as external
   interchange formats and says an orchestrator may use the contained schema
   definition for validation.
3. Section 3.6.3.4, **Grammar**, says `schema_definition` represents a schema
   definition as a string.
4. Section 3.6.10.5, **Additional Requirements**, requires that string to
   represent a valid schema definition matching the recognized external type.
5. The following section 3.6.10.5 sentence makes validation of property values
   against the schema optional (`MAY`). The frozen MUST therefore covers
   declaration compilation, not default, assignment, function-result, or
   normalized-value validation.
6. Sections 5.3.2 and 5.3.4 recognize `tosca.datatypes.json` (`json`) and
   `tosca.datatypes.xml` (`xml`). Their examples use JSON Schema Draft 4 and
   XML Schema.
7. Section 3.6.10.6 makes inherited and unmodified property constraints part
   of the effective property definition and permits refinements to add
   constraints.
8. Section 14.3 requires a conforming processor to implement section 3
   semantics and identify errors in non-conforming documents.

## Ambiguities

The property-definition keyname table in section 3.6.10.2 contains the spelling
`external-schema`, while the property-definition grammar in section 3.6.10.4
does not contain that key and section 3.6.10.5 refers to `schema`. The complete
constraint grammar and normative examples place `schema` inside `constraints`.
Puccini therefore accepts only that grammar form. A direct
`external-schema` property key remains an unsupported field; this decision does
not silently invent a second property-definition grammar.

The specification does not name every supported schema version, define a base
URI for nested schema references, require reference retrieval, define resource
limits, or define diagnostic categories. It also does not define cache
identity, network policy, timeout behavior, or validation of intrinsic
function results.

## Decision

### Schema forms and languages

- The supported declaration is the inline string operand of a `schema`
  constraint on a property whose final effective type is `json` or `xml`.
- JSON schemas compile as JSON Schema Draft 4. A missing `$schema` uses Draft
  4. A different declared dialect is rejected as an unsupported schema
  language/version rather than being silently interpreted as Draft 4.
- XML schemas compile as XML Schema 1.0. The implementation does not opt into
  XML Schema 1.1.
- A schema constraint on any other TOSCA type is an unsupported schema
  language error.
- Empty and whitespace-only declarations are invalid.
- A path, URI, URL, or repository reference is not a top-level schema form.
  Such a string is compiled as schema text and fails; it is never fetched.

### Processing phases

Structural YAML type validation remains in the read phase. Schema-language
selection and schema compilation run in the TOSCA 1.3 render hook, after type
lookup and inheritance have produced the effective property definition. This
is the earliest phase where the schema can be matched to its resolved external
data type. Compilation is independent of property assignments, defaults,
coercion, normalization, and intrinsic-function evaluation.

Every declared schema constraint is compiled, including inherited constraints.
A refinement that retains a constraint retains its compiled meaning; a newly
added schema constraint is compiled separately. Existing property-refinement
constraint-merging behavior is outside this requirement and is not changed.

### Resolution and security

- The top-level schema is inline and has the synthetic, operation-local base
  URI `urn:puccini:tosca:1.3:external-schema`.
- External resource loading is denied for both compilers. Relative references,
  `file`, HTTP(S), repository, import-relative, and CSAR-relative references
  therefore produce `schema access denied`.
- The XML parser blocks external entities, DTD loading, network access, and
  host filesystem access. The XML Schema compiler uses a deny-all filesystem.
- The JSON Schema compiler uses an injected deny-all URL loader. No default
  file or HTTP loader is reachable.
- Redirects, loopback, link-local, private networks, cloud metadata endpoints,
  device files, Unix sockets, percent-encoded traversal, and `../` traversal
  are unreachable because no external retrieval is enabled.
- Inline JSON Pointer references and in-document XSD references are allowed.
  External recursive references are denied before retrieval. Compiler cycle
  handling remains bounded by an operation context.
- Inline schema size is limited to 1 MiB. JSON/XML structural nesting is
  limited to 64; JSON traversal is limited to 100,000 nodes and 128 references.
  XML parse/compilation has a one-second deadline per unique schema. The JSON
  compiler has no cancellable context API, so it is bounded synchronously by
  the byte, depth, node, and reference limits and by the absence of I/O rather
  than by a leaking asynchronous timeout. These are implementation security
  limits, not TOSCA requirements.
- One processing operation caches compilation results, including failures, by
  canonical external type and exact schema bytes. It does not share cache data
  between parser/security contexts. Diagnostics are emitted at each property
  use in stable traversal order even when compilation is cached.
- Schema contents and retrieved local-file contents are never included in
  diagnostics.

### Error model

Diagnostics use stable category prefixes:

- `invalid external schema declaration`;
- `unsupported external schema language`;
- `external schema too large`;
- `external schema access denied`;
- `external schema reference cycle`;
- `external schema compilation failure`.

Each diagnostic identifies the property, its external type, and a non-sensitive
SHA-256 prefix identifying the inline schema bytes. A successful schema
compilation followed by a value mismatch cannot occur in the mandatory path
because value-schema validation is not enabled. If optional value
validation is added later, it must use a separate
`value-schema validation failure` category and a separate conformance decision.

### Dependencies

One engine is selected for each normative external schema language; there are
no competing engines for the same language:

- `github.com/santhosh-tekuri/jsonschema/v6` v6.0.2 (Apache-2.0) for JSON
  Schema Draft 4. It supports an explicit default draft and a custom URL
  loader, allowing all external references to be denied.
- `github.com/lestrrat-go/helium` v0.7.0 (MIT) for XML Schema 1.0. It is a
  pure-Go compiler with injectable filesystem/parser policies and secure
  parser defaults.

Neither library executes schema extensions or application code. Custom
formats, vocabularies, content decoders, XSD 1.1 features, and permissive
resource loaders are not registered.

### Version isolation

The activation hook and policy live in `tosca_v1_3`. TOSCA 2.0 does not call
the validator, and its grammar and observable behavior remain unchanged.

## Consequences

The frozen MUST becomes directly testable without network access. Malformed,
wrong-language, oversized, and externally-referencing schema declarations fail
deterministically after effective type resolution. Ordinary property values,
defaults, assignments, and functions retain their existing behavior because
the specification makes value-schema validation optional.
