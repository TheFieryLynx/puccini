# 0008: TOSCA 1.3 non-MUST processor policies

## Status

Accepted.

## Normative basis

The pinned TOSCA Simple Profile in YAML 1.3 specification is the sole
normative source. Section 3.6.8.2.3 permits an orchestrator or processor to
resolve namespace collisions as it sees fit, including treating a collision
as an error or generating a unique namespace.

## Decision

Strict TOSCA 1.3 processing treats two non-equivalent imported definitions
with the same namespace URI, local name, and version as a deterministic
namespace-phase error. Equivalent duplicate definitions remain idempotent.
The diagnostic sorts source URLs before reporting them.

The offline corpus never enables unrestricted network access. A URI that
requires unavailable or disallowed transport fails deterministically through
the existing URL policy; this is a test-execution security boundary, not a
claim that the specification prohibits network retrieval.

Unknown grammar keynames are rejected in strict mode. This is not treated as
an extension point merely because an implementation could support extensions
under an explicit compatibility mode.

## Alternatives

Generating a synthetic namespace is allowed by section 3.6.8.2.3, but would
make reference identities dependent on collision order. Retaining the first
definition would silently discard a distinct type and is therefore rejected.

## Consequences

The selected policy is stable, explicit, version-isolated by the TOSCA 1.3
namespace validator, and covered by a policy corpus case. It is not presented
as the only behavior permitted by the specification.
