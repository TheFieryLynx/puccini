# 0006: TOSCA 1.3 property-to-attribute reflection

- Status: accepted
- Date: 2026-07-28
- Applicable language version: TOSCA Simple Profile in YAML 1.3 only

## Context

Section 3.6.10.5 requires implementations to make every property defined on an
entity available as a same-named attribute. Sections 3.6.10.1, 3.6.12.1, and
3.6.12.4 repeat and explain that rule. The specification is explicit about the
name, the creation of an attribute definition, the actual/current-state role of
the attribute, and the node, node-capability, and relationship scope. It does
not completely define how to construct every field of an implicit attribute
definition or how to merge one with an explicit same-named declaration.

This record distinguishes the normative requirements from the implementation
interpretations needed by a static TOSCA processor and Puccini's normalized
model.

## Normative findings

1. Section 3.6.10.5, **Additional Requirements**, says an implementation
   SHALL make any property defined on an entity available as a same-named
   attribute.
2. Section 3.6.12.1, **Attribute and Property reflection**, says orchestrators
   automatically create attribute definitions for property definitions on the
   same entity and identifies nodes, node capabilities, and relationships.
3. Section 3.6.12 defines attributes for Node, Relationship, and Capability
   Types. Sections 3.7.7, 3.7.9, and 3.7.10 are the corresponding type
   grammars that contain both property and attribute definition maps.
4. Section 3.6.12.2 requires every attribute definition to have a data type.
   A reflected definition therefore uses the effective property's data type,
   including key and entry schemas needed to describe map and list values.
5. Sections 3.5.1 and 3.6.10.6 make inherited and refined properties part of
   the derived type's effective property definitions. Reflection consequently
   applies to the effective definitions after inheritance and refinement.
6. Section 3.6.12.4 prohibits deriving an attribute definition's `default`
   keyname from property settings or inputs. A reflected definition therefore
   has no copied property default.
7. Sections 3.6.13.2 and 4.5.1 require reflected attributes to participate in
   attribute assignment and `get_attribute` resolution.
8. Section 3.6.11.1 states that property assignments have no keynames, and
   section 3.6.11.2.1 defines only short notation. There is no normative long
   property-assignment form whose reflection could be compared with short
   notation.
9. TOSCA 1.3 type inheritance uses a single `derived_from` parent. Multiple
   type-inheritance paths are therefore not applicable.
10. The TOSCA specification does not define Puccini normalization. The
   normalized model must nevertheless retain a reflected attribute slot and
   value source so that the earlier semantic requirements are not lost.

## Ambiguous or unspecified details

The specification does not state:

- whether a property description, status, metadata, or constraint clauses are
  copied into the implicit attribute definition;
- whether a same-named explicit attribute replaces, augments, or conflicts
  with the implicit definition;
- the processor representation of an attribute's current value before an
  orchestrator has instantiated the resource;
- whether the rendered property assignment is the initial current value when
  no explicit attribute value or attribute default exists.

Two broad conflict interpretations are possible:

1. Always create a second implicit declaration. This cannot be represented by
   the grammar's name-keyed attribute map and leaves resolution ambiguous.
2. Treat the explicit declaration as the concrete representation of the
   required same-named attribute, provided its type is identical to the
   effective property type; otherwise reject the inconsistent type contract.

The second interpretation preserves deterministic name lookup and the
property's typed actual-state contract.

## Decision

For TOSCA 1.3:

- Reflection applies to effective Node Type, Relationship Type, Capability
  Type, and node Capability Definition property maps. It does not apply to data,
  artifact, group, policy, or project-specific structures that have no
  normative attribute-definition/instance semantics.
- Reflection runs after hierarchy construction and inheritance, before
  rendering assignments. It does not mutate the source YAML document.
- Each implicit definition is a distinct attribute-definition object. It
  copies the effective property name, data type, description, key schema, and
  entry schema. Schema objects are independently cloned.
- Property constraint clauses, property `required`, property `default`,
  property metadata, and property status are not copied. Description copying
  is an implementation interpretation: it preserves documentation for the
  same named state without changing validation.
- A same-named explicit attribute is retained when its effective data type is
  identical to the effective property data type. Its explicitly declared
  fields take precedence. A different data type is a deterministic rendering
  error reported at the explicit attribute definition.
- Inheritance and property refinement are completed before reflection. Each
  type receives one reflected definition based on its final effective property
  type; inherited paths do not duplicate definitions.
- During rendering, an explicit attribute assignment has first precedence and
  an explicit attribute-definition default has second precedence. Otherwise,
  the rendered property value (including an applied property default or an
  unevaluated intrinsic function) is used as the initial reflected current
  value. An absent optional property yields an attribute slot with no value.
  Treating the rendered property value as the initial current value is a
  Puccini processor interpretation; an orchestrator may replace it with the
  actual runtime value.
- Property and attribute normalized values are independently normalized; they
  do not share a mutable normalized value object.
- `get_attribute` resolves the effective attribute definition. It no longer
  uses a separate property-map fallback. Evaluation reads the normalized
  attribute value, so a function-valued property becomes visible through the
  reflected attribute after function evaluation.
- SOURCE and TARGET remain runtime endpoint contexts under section 4.5.1.
  Static validation confirms the context but cannot select an endpoint type
  when the relationship is not bound to a single instance.

## Consequences

The effective-type hook is isolated in the TOSCA 1.3 grammar. Shared rendering
infrastructure recognizes only definitions explicitly marked by that hook, so
TOSCA 2.0 behavior does not change. Reflection is idempotent, definition maps
remain name-keyed, diagnostics are deterministic, and normalization preserves
the reflected state required by `get_attribute`.
