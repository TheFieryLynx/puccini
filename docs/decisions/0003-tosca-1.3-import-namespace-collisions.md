# TOSCA 1.3 import namespace collision policy

## Status

Accepted for strict TOSCA 1.3 processing.

## Context

TOSCA Simple Profile in YAML 1.3, section 3.1.3.1, “Additional
Requirements”, requires local names to be unique and requires definitions
identified by the same namespace URI, local name, and version to be
equivalent.

Section 3.6.8.2.3, “Requirements”, also states that a TOSCA processor may
resolve import namespace collisions as it sees fit, including by reporting an
error. It does not prescribe precedence between conflicting imports.

## Decision

Strict TOSCA 1.3 processing uses deterministic error resolution:

- two different imports cannot claim the same non-empty
  `namespace_prefix`;
- conflicting unqualified imported or local names are reported as ambiguous;
- importing the exact same document more than once is idempotent;
- different prefixes may refer to definitions in the same namespace URI;
- distinct resources that claim the same namespace URI, local name, version,
  and definition kind are rejected as an import collision; this conservative
  policy prevents non-equivalent definitions from coexisting and does not
  attempt to prove semantic equivalence between different YAML encodings;
- merge and diagnostic order is based on canonical import and entity names,
  not Go map iteration order.

This is a processor collision-resolution policy permitted by section
3.6.8.2.3. It is not presented as a requirement that every TOSCA processor
must choose the same policy.

## Consequences

- No import silently overrides a conflicting local or imported definition.
- Duplicate and collision diagnostics are repeatable across runs.
- Namespace-qualified lookup remains explicit and version-specific.
- Shared sorting code affects order only; it does not add TOSCA 1.3 grammar
  rules to TOSCA 2.0.
