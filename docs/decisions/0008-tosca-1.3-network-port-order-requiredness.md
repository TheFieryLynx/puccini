# 0008: TOSCA 1.3 Network Port order requiredness

- Status: accepted
- Date: 2026-07-28
- Applicable language version: TOSCA Simple Profile in YAML 1.3 only

## Context

The pinned TOSCA 1.3 specification is internally inconsistent about the
requiredness of `tosca.nodes.network.Port.properties.order`.

Section 8.5.2.1, **Properties**, shows `order` with `Required` equal to `no`.
Section 8.5.2.3, **Definition**, gives the normative type definition as:

```yaml
order:
  type: integer
  required: true
  default: 0
  constraints:
    - greater_or_equal: 0
```

The frozen atomic requirement `TOSCA13-8.5.2.3-008` specifically represents
the `required: true` statement in section 8.5.2.3. The bundled profile instead
declared `required: false`, so its ordinary effective type definition did not
match that frozen requirement.

## Competing interpretations

1. Treat the property table in section 8.5.2.1 as authoritative and retain
   `required: false`.
2. Treat the machine-readable normative type definition in section 8.5.2.3 as
   authoritative and use `required: true`.
3. Treat the contradiction as making requiredness unusable and avoid choosing
   either value.

The third option cannot produce a concrete normative profile. The first option
would leave the explicitly targeted frozen MUST record non-compliant.

## Decision

Puccini's strict TOSCA 1.3 bundled profile follows section 8.5.2.3 and declares
`order.required: true`.

This is an implementation interpretation resolving contradictory local text;
it is not presented as an unambiguous statement shared by both section
8.5.2.1 and section 8.5.2.3.

The related `type: integer`, `default: 0`, and `greater_or_equal: 0` definition
remain unchanged. Because a default exists, omitting an explicit `order`
assignment remains valid: rendering supplies the default. Requiredness is
observable in the effective property definition and in refinement semantics:
a derived type cannot weaken the property to `required: false`.

The correction is confined to the bundled TOSCA 1.3 profile. TOSCA 2.0 profile
definitions and property semantics do not change.

## Consequences

Direct conformance tests load the bundled profile through the normal parser,
namespace, hierarchy, inheritance, and rendering path. They verify the
effective requiredness, parent, property set, type, default, constraint,
attribute, and requirements; they also verify default/zero assignments and
rejection of an optional refinement.

The table/definition contradiction remains in the pinned normative source,
which is not modified.
