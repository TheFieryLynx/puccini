# 0009: TOSCA 1.3 data type root shape

## Status

Accepted.

## Context

TOSCA 1.3 section 3.7.6.3, "Additional Requirements", says that a valid data
type definition MUST have either a valid `derived_from` declaration or at
least one valid property definition. The same section says that an explicitly
provided `properties` keyname SHALL contain one or more valid property
definitions.

Section 5.3.1, however, normatively defines `tosca.datatypes.Root` with only a
description. It has neither `derived_from` nor properties because it is the
root from which all complex data types derive. Puccini's implicit primitive
data types are likewise processor roots represented by internal metadata,
rather than service-template data type declarations.

Applying the first rule literally to bundled roots would make the normative
profile impossible to load. The specification does not state an explicit root
exception in section 3.7.6.3.

## Decision

For TOSCA 1.3 service-template and imported data type declarations, enforce
the section 3.7.6.3 alternatives exactly:

- a declaration must provide `derived_from` or a non-empty `properties` map;
- if `properties` is present, it must contain at least one entry;
- structural validity of property definitions is checked by the read phase;
- validity of a `derived_from` name is checked by the existing lookup and
  hierarchy phases.

The exact bundled `tosca.datatypes.Root` and bundled primitive definitions
identified by processor-owned `puccini.type` metadata are exempt from only the
"parent or property" shape check. Both must also be loaded from
`internal:/profiles/`. Other bundled data types remain subject to the check.
The exemption cannot be selected by a service-template author and does not
suppress the non-empty check when a bundled definition explicitly supplies
`properties`.

This root exemption is an implementation interpretation resolving the
contradiction between sections 3.7.6.3 and 5.3.1; it is not presented as
explicit wording from the specification.

## Consequences

The check remains isolated in the TOSCA 1.3 reader. TOSCA 2.0 behavior is
unchanged. User declarations cannot use metadata or a type name to bypass the
check because the exception depends on the processor-owned internal profile
URL.
