# TOSCA 1.3 fixed property refinement notation

TOSCA 1.3 sections 3.6.10.6 (Refining Property Definitions) and 3.6.14.2
(Grammar), in the pinned specification, permit parameter notation for property
refinements, including a short fixed value and a `value` field. A fixed value
cannot subsequently change. Repeating the same value does not change it; changing
an otherwise unused default does not replace the fixed value. The default still
has to satisfy its declared type and constraints.

Short map values and long parameter definitions can have the same YAML shape.
The processor interprets a map containing a recognized definition key as long
notation. Use an explicit `value` wrapper for a literal map with such keys.
This disambiguation is an implementation decision, not an additional normative
restriction on map property values. Empty maps retain the existing interpretation
as empty refinements; `value: {}` expresses an empty fixed map.

The fixed value supplies the effective initial property value. A separate
TOSCA 1.3 assignment policy enforces finality. Added constraints are conjoined
with inherited constraints. Tests in `re_audit_property_refinement_test.go`
cover fixed values, short maps/lists/expressions, defaults, successive
refinements, type narrowing, and normalized values and validators. TOSCA 2.0
has separate normative rules and does not enable these 1.3 policy callbacks.
